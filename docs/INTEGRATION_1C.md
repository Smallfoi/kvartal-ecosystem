# ТЗ: Интеграция 1С ↔ МАТА (обмен данными каталога и заказов)

**Документ для разработчика 1С.** Цель — чтобы за одно прочтение было понятно:
как устроен обмен, в каком формате, какие данные нужны **сейчас**, какие
**потом**, и где чья зона ответственности.

- **Версия:** 1.0 (черновик к согласованию)
- **Стороны:** 1С (источник товаров/цен/остатков) ↔ МАТА (бэкенд Django + витрина: приложение SportStore и сайт МАТА)

---

## 0. Коротко (TL;DR)

1. **1С — источник правды** по товарам, ценам, остаткам. МАТА забирает это и показывает на витрине.
2. У каждой позиции нужен **неизменный идентификатор** (GUID/артикул) — по нему обновляем, без дублей.
3. **Сейчас** нужны: категории + карточки товаров (наименование, бренд, описание, размеры/цвета, фото) + **цены и числовой остаток**. Приём всех трёх потоков работает.
4. **Потом:** остаток по складам, штрихкоды, вес/габариты, типы цен/акции, и **выгрузка заказов МАТА → 1С** со статусами. (Остаток по размеру уже принимается — см. §2 и §3.3.)
5. **Витринное** (новинка/рекомендуемое/публикация, отзывы, баллы) МАТА ведёт сам — из 1С **не присылать**.
6. Делим потоки: **«Каталог»** (меняется редко) и **«Цены+Остатки»** (меняется часто) — выгружаются отдельно и с разной периодичностью.

## 1. Архитектура и зоны ответственности

```
┌──────┐  выгрузка    ┌───────────────────────┐  забор    ┌──────────────┐   ┌────────────────────┐
│  1С  │ ───────────▶ │ промежуточная БД /    │ ───────▶ │ бэкенд МАТА  │──▶│ витрина:           │
│      │  (по         │ обменный формат       │ (по      │ (Django+API) │   │ приложение + сайт  │
│      │  расписанию) │ — «накопитель»        │ расписан.)│              │   │                    │
└──────┘              └───────────────────────┘          └──────────────┘   └────────────────────┘
       ◀─────────────────── заказы МАТА → 1С (этап 2) ───────────────────
```

**Кто за что отвечает:**

| Данные | Источник правды | Кто меняет |
|---|---|---|
| Номенклатура, цены, остатки, фото, описание, размеры/цвета | **1С** | 1С (МАТА только читает) |
| Категории (структура) | **1С** | 1С |
| Заказы (факт продажи) | МАТА создаёт → передаёт в 1С (этап 2) | МАТА + 1С (статусы) |
| Витрина: «Новинка»/«Рекомендуемое»/«Опубликован» | **МАТА** | МАТА |
| Отзывы, рейтинг, баллы лояльности, баннеры, контент | **МАТА** | МАТА |

> Принцип: **1С не присылает витринные поля** (см. §6), иначе обмен затрёт ручные настройки магазина.

## 2. Способ обмена

> **Выбран и работает вариант А (REST).** С 2026-08-31 приём включён на проде:
>
> | Что | Адрес |
> |---|---|
> | Категории | `POST https://api.mata-club.ru/v1/integrations/1c/categories` |
> | Карточки товаров | `POST https://api.mata-club.ru/v1/integrations/1c/catalog` |
> | Цены и остатки | `POST https://api.mata-club.ru/v1/integrations/1c/prices` |
> | Проверка связи | `GET  https://api.mata-club.ru/v1/integrations/1c/status` |
>
> **Порядок при первой выгрузке: категории → каталог → цены.** Товар с категорией,
> которой у МАТА ещё нет, сохранится, но не покажется ни в одном разделе витрины.
> Такие категории возвращаются в отчёте в `unknownCategories` и попадают в журнал
> обмена как замечание — это не молчаливая потеря.
>
> Авторизация — постоянный заголовок `Authorization: Bearer <токен>` (токен выдаёт владелец;
> обновлять и подтверждать вторым фактором не нужно). Тело: `{"products": [...]}` /
> `{"prices": [...]}` либо просто массив. В ответ приходит отчёт: `received`, `created`,
> `updated`, `keptByOwner`, `errors`.
>
> **Право вето владельца (D-62).** Если владелец поменял поле в Конструкторе МАТА
> (цена, старая цена, описание, размеры), следующая выгрузка это поле **не перезаписывает** —
> оно приходит в отчёте в `keptByOwner`. Значение из 1С при этом сохраняется и показывается
> рядом; владелец может вернуть поле под управление 1С кнопкой «вернуть как в 1С».
> **Остаток — исключение:** он всегда берётся из 1С.
>
> **Остаток по размерам работает.** Если в `prices` приходит массив `variants` с
> `size` и `stock`, МАТА раскладывает остаток по размерам: на витрине размер без
> остатка показан, но зачёркнут и не выбирается. Общий остаток при этом считается
> суммой вариантов. Один размер в нескольких строках (разные цвета или склады)
> складывается. Если прислать общий `stock` без вариантов — прежняя разбивка
> очищается, потому что она уже неправда.
>
> **Журнал обмена** ведётся на стороне МАТА: админка → «Мониторинг» → «Журнал обмена»
> (дата, операция, статус, сколько получено/добавлено/обновлено, замечания; хранится 90 дней).


Состав данных (поля) **не зависит** от транспорта. Транспорт согласуем; рекомендуемый — REST,
но под описанную задачу («1С пишет в отдельную БД, МАТА забирает») подходит вариант Б.

| Вариант | Как | Плюсы | Когда |
|---|---|---|---|
| **А. REST API (рекомендуется)** | МАТА даёт endpoint, 1С шлёт `POST` пакетами по расписанию | просто, без общей БД, мгновенная валидация | если 1С умеет HTTP-запросы |
| **Б. Промежуточная БД** | 1С пишет в таблицы общей БД, МАТА читает по расписанию | привычно для 1С, «накопитель» | как описал заказчик (см. §8) |
| **В. Файловый обмен** | 1С кладёт JSON/CommerceML в папку, МАТА забирает | оффлайн-дружелюбно | если нет прямого канала |

**Общие правила для любого варианта:**

- **Формат данных:** JSON (предпочтительно) или CommerceML/XML — МАТА распарсит. Кодировка **UTF-8**.
- **Ключ:** см. §3. Обновление по ключу — **идемпотентно** (повтор той же позиции = update, не дубль).
- **Дельта:** присылать **изменённые** позиции (по `updatedAt`/дате изменения) + раз в сутки **полную** выгрузку для сверки.
- **Два потока, разная частота:**
  - «Каталог» (карточки) — редко (раз в час/по изменению).
  - «Цены + Остатки» — часто (раз в 5–15 мин).
- **Удаление/снятие с продажи:** не удалять физически, а слать признак `active=false` (МАТА скроет с витрины).

## 3. ЭТАП 1 — данные, нужные СЕЙЧАС

### 3.0. Ключ синхронизации (самое важное)

У каждой позиции — **неизменный уникальный идентификатор** из 1С:
- `id` — **GUID номенклатуры** (предпочтительно) или **Артикул**. Не меняется при правке товара.
- Если есть варианты (размер/цвет) как отдельные характеристики/позиции 1С — у каждого варианта **свой** `variantId` (GUID характеристики или артикул варианта). Нужен для остатка по размеру.

### 3.1. Справочник «Категории»

> **Реализовано** (02.09.2026): `POST /v1/integrations/1c/categories`.
> 1С ведёт `name`, `sort`, `parentId`. Эмодзи и фото категории — наши, выгрузка их
> не трогает. Дерево пока храним, но витрина плоская. Категорию, пропавшую из
> выгрузки, МАТА не удаляет: на неё ссылаются товары.

| Поле | Тип | Обяз. | Пример | Описание |
|---|---|:---:|---|---|
| `id` | строка | **да** | `"shoes"` или GUID | ключ категории (стабильный) |
| `name` | строка | **да** | `"Кроссовки"` | название для витрины |
| `parentId` | строка | нет | `null` | родитель (если дерево категорий) |
| `sort` | число | нет | `10` | порядок отображения |

**Пример JSON:**
```json
[
  { "id": "shoes",   "name": "Кроссовки", "parentId": null, "sort": 10 },
  { "id": "tshirts", "name": "Футболки",  "parentId": null, "sort": 20 }
]
```

### 3.2. Справочник «Товары» (карточка — меняется редко)

| Поле | Тип | Обяз. | Пример | Описание |
|---|---|:---:|---|---|
| `id` | строка | **да** | `"SS-0042"` / GUID | ключ синхронизации |
| `article` | строка | **да** | `"AR-X1-BLK"` | артикул (SKU) |
| `name` | строка | **да** | `"Кроссовки Air Runner X1"` | наименование |
| `categoryId` | строка | **да** | `"shoes"` | ссылка на категорию (§3.1) |
| `brand` | строка | желат. | `"МАТА"` | бренд/производитель |
| `description` | текст | желат. | `"Лёгкие беговые…"` | описание |
| `unit` | строка | нет | `"шт"` | единица измерения |
| `sizes` | массив строк | да* | `["40","41","42"]` | размеры (*для одежды/обуви) |
| `colors` | массив строк | желат. | `["Чёрный","Белый"]` | цвета |
| `images` | массив URL | желат. | `["https://…/1.jpg"]` | фото: первое — главное |
| `active` | булево | **да** | `true` | в продаже / в архиве |
| `updatedAt` | дата-время ISO | желат. | `"2026-06-28T10:00:00Z"` | для дельта-обмена |

**Пример JSON (одна карточка):**
```json
{
  "id": "SS-0042",
  "article": "AR-X1",
  "name": "Кроссовки Air Runner X1",
  "categoryId": "shoes",
  "brand": "МАТА",
  "description": "Лёгкие беговые кроссовки с амортизацией.",
  "unit": "шт",
  "sizes": ["40", "41", "42", "43"],
  "colors": ["Чёрный", "Белый"],
  "images": [
    "https://1c-exchange/staw/AR-X1-1.jpg",
    "https://1c-exchange/staw/AR-X1-2.jpg"
  ],
  "active": true,
  "updatedAt": "2026-06-28T10:00:00Z"
}
```

### 3.3. «Цены и остатки» (меняется часто — отдельный поток)

Минимум этапа 1 — **по товару** (общий остаток). Желательно сразу — **по варианту** (размер).

| Поле | Тип | Обяз. | Пример | Описание |
|---|---|:---:|---|---|
| `id` | строка | **да** | `"SS-0042"` | товар (ключ из §3.2) |
| `variantId` | строка | желат. | `"SS-0042-41"` | вариант (размер/цвет), если есть |
| `size` | строка | желат. | `"41"` | размер варианта |
| `price` | число | **да** | `11990` | розничная цена |
| `oldPrice` | число | нет | `13990` | старая цена (если есть скидка) |
| `currency` | строка | нет | `"RUB"` | валюта |
| `stock` | целое | **да** | `7` | остаток к продаже (число!) |

> Сейчас в МАТА остаток хранится как «в наличии: да/нет». **Нужна реальная цифра** `stock`.
> Если 1С отдаёт остаток только по варианту — МАТА сам просуммирует в общий.

**Пример JSON (остатки по размерам):**
```json
{
  "id": "SS-0042",
  "price": 11990,
  "oldPrice": 13990,
  "currency": "RUB",
  "variants": [
    { "variantId": "SS-0042-40", "size": "40", "stock": 3 },
    { "variantId": "SS-0042-41", "size": "41", "stock": 0 },
    { "variantId": "SS-0042-42", "size": "42", "stock": 7 }
  ]
}
```

## 4. ЭТАП 2+ — понадобится ПОТОМ (развитие)

**Остатки и логистика:**
- Остаток по **каждому варианту** (размер×цвет) и по **нескольким складам/точкам**.
- **Резервирование** остатка под оформленный заказ (чтобы не продать одно и то же дважды).
- **Штрихкод (EAN-13)** — для сканирования, касс, будущего сопоставления.
- **Вес и габариты** (длина/ширина/высота) — для расчёта стоимости доставки (СДЭК / Почта России).

**Цены и акции:**
- Несколько **типов цен** (розница / акция / по карте лояльности).
- **Скидки/промо** с периодом действия (дата начала–окончания).
- **Ставка НДС** и признак налогообложения — для чеков и фискализации.

**Прочее:**
- **Контрагенты/клиенты:** связка покупателя МАТА (по телефону) с контрагентом 1С — для документов и истории.
  ⚠️ Персональные данные: репозиторий публичный, доступ к промежуточной БД ограничить, лишнее не выгружать.
- **Возвраты/обмены**, **фискализация** (чеки), интеграция **оплаты** (ЮKassa) — позже.

## 5. Заказы МАТА → 1С (обратный поток, этап 2)

Когда покупатель оформляет заказ на витрине, МАТА передаёт его в 1С (документ «Заказ покупателя»),
а 1С возвращает **статус** обратно. Предварительный состав:

| Поле | Тип | Описание |
|---|---|---|
| `orderId` | строка | номер заказа МАТА (ключ, идемпотентность) |
| `createdAt` | дата-время | дата оформления |
| `customer` | объект | телефон (+ имя), способ доставки, адрес |
| `items[]` | массив | `{ id/article, variantId, size, qty, price }` |
| `total` | число | сумма заказа |
| `pointsRedeemed` | число | списано баллов лояльности (информативно) |
| `payment` | строка | способ оплаты |
| `delivery` | строка | способ/адрес доставки |

**Статусы обратно из 1С → МАТА:** `accepted` (принят) → `assembled` (собран) → `shipped` (отгружен) →
`delivered` (доставлен) / `canceled` (отменён). МАТА покажет статус покупателю и пришлёт уведомление.

**Пример JSON (заказ МАТА → 1С):**
```json
{
  "orderId": "МАТА-581431",
  "createdAt": "2026-06-28T12:30:00Z",
  "customer": { "phone": "+79148278470", "name": "Михаил" },
  "items": [
    { "id": "SS-0042", "variantId": "SS-0042-42", "size": "42", "qty": 1, "price": 11990 }
  ],
  "total": 11990,
  "pointsRedeemed": 0,
  "payment": "online",
  "delivery": "cdek",
  "address": "Якутск, ул. Ленина 1, кв. 5"
}
```

## 6. Зона МАТА — из 1С присылать НЕ нужно

Эти поля ведёт магазин; 1С их **не отправляет** (иначе перезатрёт настройки витрины):

- Маркетинговые флаги: **«Новинка»**, **«Рекомендуемое»**, **«Опубликован на витрине»**.
- **Рейтинг и отзывы** товара (пишут покупатели).
- **Баллы лояльности**, их начисление и трата.
- **Баннеры**, контент и оформление сайта/приложения.

## 7. Регламент обмена

| Параметр | Значение |
|---|---|
| Кодировка | UTF-8 |
| Формат | JSON (или CommerceML/XML) |
| Поток «Каталог» (карточки, категории) | по изменению / раз в час |
| Поток «Цены + Остатки» | часто — раз в 5–15 мин |
| Тип выгрузки | дельта по `updatedAt` + раз в сутки полная (сверка) |
| Идемпотентность | обновление по ключу `id`/`variantId`, без дублей |
| Снятие с продажи | `active=false` (не физическое удаление) |
| Ошибки | позиция с ошибкой пропускается и логируется; остальные применяются |

## 8. Промежуточная БД (если выбран вариант Б)

Если 1С выгружает в отдельную БД-«накопитель», МАТА читает такие таблицы (примерная схема —
поля те же, что в §3, имена согласуем):

**`catalog_categories`**
| колонка | тип | примечание |
|---|---|---|
| `id` | varchar PK | ключ |
| `name` | varchar | |
| `parent_id` | varchar null | |
| `sort` | int | |
| `updated_at` | timestamp | для дельты |

**`catalog_products`** (карточка)
| колонка | тип | примечание |
|---|---|---|
| `id` | varchar PK | ключ синхронизации |
| `article` | varchar | SKU |
| `name` | varchar | |
| `category_id` | varchar | → categories.id |
| `brand` | varchar | |
| `description` | text | |
| `sizes` | json/varchar | список |
| `colors` | json/varchar | список |
| `images` | json/varchar | список URL |
| `active` | bool | |
| `updated_at` | timestamp | дельта |

**`catalog_stock_prices`** (часто меняется)
| колонка | тип | примечание |
|---|---|---|
| `product_id` | varchar | → products.id |
| `variant_id` | varchar null | размер/цвет (этап 1.5+) |
| `size` | varchar null | |
| `price` | numeric | розница |
| `old_price` | numeric null | скидка |
| `stock` | int | остаток |
| `updated_at` | timestamp | дельта |

> МАТА читает по `updated_at` (что изменилось с прошлой синхронизации) и обновляет каталог.

## 9. Чеклист для согласования на старте

1. **Идентификатор** позиции: GUID номенклатуры или артикул? (и для вариантов размер/цвет).
2. **Транспорт:** REST (А) / промежуточная БД (Б) / файлы (В) — и доступ к ней.
3. **Формат:** JSON или CommerceML/XML.
4. **Где хранятся фото** и как отдаются (ссылки или файлы).
5. **Остаток:** общий по товару (минимум) или сразу по размерам (лучше).
6. **Расписание** выгрузок: каталог и цены/остатки.
7. Подтвердить **состав этапа 1** (этот документ) и зафиксировать, что этап 2 — позже.

---

### Резюме одной фразой
> Дайте **стабильный id** каждой позиции и по нему — **наименование, категорию, цену, остаток (число),
> размеры/цвета, фото, признак «активен»** (этап 1). Дальше — **остаток по размеру и складам, штрихкоды,
> вес/габариты, типы цен/акции и выгрузку заказов из магазина обратно в 1С со статусами** (этап 2).
> Витринные вещи (новинка/рекомендуемое/публикация, отзывы, баллы) магазин ведёт сам — слать не нужно.
