# Конструктор витрины: общие данные + раздельная раскладка (сайт / приложение)

**Документ-план (к согласованию).** Как сделать в админ-панели визуальный «конструктор
витрины»: перетаскивание товаров, правка прямо в превью, раздельная раскладка для сайта
и приложения — **без дублирования данных и без риска для ядра**.

- **Стороны/каналы:** Сайт STAW, мобильное приложение SportStore. Общий бэкенд (Django).
- **Статус:** планирование, ничего не реализовано.

---

## 0. Коротко (TL;DR)
1. **Данные товара — общие** (одна запись, редактируется один раз, меняется везде). У нас уже так.
2. **Раскладка/порядок — раздельные** для сайта и приложения (разные площадки — разный вид).
3. **Правка прямо в превью:** клик по товару → панель (описание, цена, старая цена, наличие,
   размеры, фото, публикация) → сохранил → оба превью обновились.
4. **Дублирование невозможно** — товар физически один; «поменял тут, а там осталось» у нас не бывает.
5. Так работают большие (**headless commerce**): единый каталог данных + отдельный мерчендайзинг на канал + превью на устройство.

---

## 1. Принцип: разделяем ДАННЫЕ и РАСКЛАДКУ

| | Что это | Сайт и приложение |
|---|---|---|
| **ДАННЫЕ товара** | наименование, описание, цена, старая цена, наличие, размеры, цвета, фото | **общие — одно и то же везде** |
| **РАСКЛАДКА** | порядок товаров, «на главной / рекомендуем», расположение секций | **раздельные — свои для каждой площадки** |

Правишь **данные** — меняется на сайте и в приложении сразу. Крутишь **порядок** — отдельно
под каждую площадку (на сайте одна сетка, в приложении другая раскладка).

---

## 2. Разделение полей (главное — чтобы не было дублей)

### 2.1. Централизованные (общие) — меняются во всех каналах сразу
Физически это одна запись `Product`, поэтому расхождений быть не может:

- Наименование
- Описание
- Цена, старая цена (скидка)
- В наличии
- Размеры, цвета
- Фото (главное + дополнительные)
- Бренд, категория
- Артикул (когда добавим из 1С)
- Рейтинг и кол-во отзывов (считаются из отзывов — автоматически)

### 2.2. Пер-площадка (раздельно для сайта и приложения)
- **Порядок товара** (`sort_site` / `sort_app`)
- **«Рекомендуемое / на главной»** на конкретной площадке *(по решению — см. §8)*
- **Раскладка секций главной** (баннеры/категории/блоки) — раздельно *(этап позже, §7)*

### 2.3. На будущее (необязательно) — «переопределение под площадку»
Если однажды понадобится **другое фото или описание именно для приложения** — делается как
необязательный override поверх общего. **По умолчанию всё общее**, чтобы не плодить дубли.

---

## 3. Как это работает

- Открываешь **превью сайта** → видишь витрину как на сайте → перетаскиваешь товары под сайт.
  Что-то не нравится → клик по товару → правишь описание/цену/наличие → **сразу видно**.
- Открываешь **превью приложения** → там **другая раскладка** → настраиваешь порядок под
  приложение **отдельно** → правишь тот же товар → изменение данных видно и тут, и на сайте.
- **Порядок раздельный, данные общие** — никаких расхождений.

Перетаскивание = смена **порядка в сетке** (визуально как плитки на рабочем столе), **не**
произвольные координаты X/Y — иначе ломается адаптив под разную ширину экранов.

---

## 4. Как это делают большие корпорации (headless commerce)
Индустриальный стандарт — ровно наш подход:

- **PIM (единый каталог товаров)** — один источник правды по данным товара; правка расходится
  по всем каналам. Это наш Django-каталог.
- **Мерчендайзинг на канал** — у каждого канала (web / iOS / Android) своя витрина и свой
  порядок, но **данные общие** (Amazon, Nike, Shopify, commercetools, Salesforce Commerce).
- **CMS с превью по устройствам** (Contentful, Storyblok, Sanity) — контент отдельно от вёрстки,
  редактор двигает блоки с **живым превью «как на web / как в приложении»**.

Вывод: **общие данные + раздельная презентация по каналам + превью на канал**. Мы к этому
уже готовы на ~80% (данные централизованы).

## 5. Что уже готово / что добавить

**Уже есть:**
- Один `Product` в общем бэкенде → и сайт, и приложение читают одну запись (данные централизованы).
- Поля `sort`, `is_published`, цена/старая цена/описание/фото/наличие; модель `Banner` (акции).
- Превью-страницы в админке (`preview_site.html`, `preview_app.html`) + режим черновиков `?preview=1`.

**Добавить:**
1. **Раздельный порядок** по площадкам (`sort_site`, `sort_app`) + параметр API `?platform=site|app`.
2. **Перетаскивание** товаров в превью (библиотека SortableJS) + эндпоинт «переупорядочить пачкой».
3. **Панель правки в превью** — редактирует центральный товар; оба превью обновляются.

## 6. Архитектура и что затрагивается

| Слой | Что нужно | Риск |
|---|---|---|
| **Данные (Product)** | централизация уже есть; +поля `sort_site`, `sort_app` (миграция) | низкий |
| **API каталога** | добавить параметр `?platform=site\|app` (порядок по нужному полю); без платформы — как сейчас | низкий, **обратно совместимо** |
| **Сайт (catalog.js)** | слать `?platform=site` (1 строка); необязательно для базовой работы | минимальный |
| **Приложение (SportStore)** | слать `?platform=app` (1 строка) | минимальный |
| **Админка** | новая страница «Конструктор витрины» + эндпоинты reorder/patch (изолировано) | средний |
| **Превью** | iframe сайта уже есть; авто-обновление после правки; превью приложения — Flutter web | средний |
| **Ядро (auth / loyalty / orders)** | **не трогаем** | нет |

**Вывод:** это надстройка над готовыми данными. Контракты `auth/profile/loyalty/orders` не
меняются; клиентские приложения по данным менять не нужно — результат появляется сам.

## 7. Пофазный план и объём

- **Фаза 0 — уже готово:** данные централизованы (один `Product`), превью-страницы есть.
- **Фаза 1 — Раздельный порядок.** Поля `sort_site`/`sort_app` + `?platform=` в API + drag-reorder
  товаров на странице (SortableJS) + эндпоинт reorder. Сайт/приложение шлют свою площадку.
  **Объём: S–M.**
- **Фаза 2 — Редактор-в-превью (сайт).** Страница «Конструктор витрины (сайт)»: превью сайта +
  drag-порядок + клик по товару → панель правки (описание/цена/старая цена/наличие/размеры/фото/
  публикация) → сохранение в центральный товар → превью обновляется. **Объём: M.**
- **Фаза 3 — Превью приложения.** То же для приложения (Flutter web в iframe, свой порядок).
  **Объём: M–L** (Flutter-web сборка — самая тяжёлая часть).
- **Фаза 4 — На будущее.** Раскладка секций главной как блоки; платформенные override данных. **Объём: L.**

**Рекомендация:** идти по фазам. Фаза 1 даёт раздельный порядок дёшево; Фаза 2 — полный редактор
для сайта; приложение (Фаза 3) — в конце, оно дороже и не блокирует пользу.

---

## 8. Решения владельца (согласовать перед стартом)
1. **Публикация** товара — общая для всех каналов или **раздельная** (например, опубликован на
   сайте, но пока не в приложении)? По умолчанию — общая.
2. **«Рекомендуемое / на главной»** — общий флаг или **раздельный** по площадкам?
3. **Раскладка секций** главной (двигать блоки «баннеры/категории/рекомендуем») — нужна сейчас
   или отложить в Фазу 4?
4. **Дизайн/бренд** не трогаем (директива D-01) — конструктор влияет только на данные и порядок.

---

## 9. Итог
- **Данные — централизованы** (уже так): правишь один раз, меняется везде, дублей нет по устройству.
- **Раскладка — раздельная** по площадкам: сайт и приложение выглядят по-своему, порядок свой.
- **Правка в превью:** видишь как будет выглядеть → не нравится → тут же исправил.
- Затрагиваем только каталог + админку; **ядро экосистемы не трогаем**; всё **обратно совместимо** и делается **фазами**.
