# Базовый аудит безопасности бэкенда (launch-gate §13)

Дата: 2026-08-18. Метод: чтение кода в чувствительных местах (деньги, баллы, личные
данные, загрузка файлов, аутентификация) + `manage.py check --deploy` в прод-конфигурации
+ проверка авторизации на изменяющих эндпоинтах. Каждая находка закрыта тестом.

> Это не пентест и не заключение аудитора. Это внутренняя проверка своими силами,
> покрывающая типовые классы ошибок веб-бэкенда.

---

## Найдено и исправлено

### 1. Сумму заказа определял клиент — критично

**Было:** `POST /v1/orders` брал `total` из тела запроса и на веру. По нему же выставлялся
счёт в ЮKassa и начислялись баллы. Корзину на 50 000 ₽ можно было оформить с `total: 1`,
заплатить рубль и получить товар — прямая потеря денег.

**Стало:** `orders/pricing.py` пересчитывает минимально допустимую сумму по **ценам
каталога** (товар × количество) минус фактически списанные баллы — по реестру транзакций,
а не по заявлению клиента. Заниженная сумма отклоняется с 400. Превышение допускается:
доставку считает клиент, и правил доставки у бэкенда пока нет.

Дополнительно: оплаченный заказ нельзя переоформить с другой суммой (409) — иначе её
меняли бы задним числом.

**Тесты:** 7 — занижение, верная сумма, количество позиций, реально списанные баллы,
заявленные но не списанные баллы, товар вне каталога, доставка сверху.

### 2. Телефон — логин, но менялся без подтверждения

**Было:** `PATCH /v1/profile` принимал `phone`, а вход по SMS ищет аккаунт именно по
номеру, причём поле не уникально. Атакующий присваивал своему аккаунту чужой номер —
дальше вход владельца по SMS мог привести в аккаунт атакующего.

**Стало:** телефон меняется только при первичном заполнении пустого поля, и то с проверкой,
что номер не занят (409). Смена существующего номера игнорируется — для неё нужен отдельный
сценарий с подтверждением по SMS.

**Тесты:** 3 — перехват чужого номера, законное первичное заполнение, занятый номер.

### 3. Тип загружаемого файла определялся по словам клиента

**Было:** проверялись `Content-Type` из заголовка и расширение из имени файла — и то, и
другое присылает клиент. Можно было положить в media `x.html` с любым содержимым: nginx
отдал бы его как страницу, то есть хранимый XSS на домене медиа.

**Стало:** `common/uploads.py` определяет тип по сигнатуре файла (magic bytes), имя и
заголовок игнорируются, расширение подставляет сервер. Разрешены JPEG, PNG, GIF, WebP;
лимит 5 МБ сохранён. Применено во всех четырёх точках загрузки: аватар, фото отзыва,
логотип и обложка клуба.

**Тесты:** 3 — HTML под видом PNG, настоящий PNG с ложным именем и типом, превышение размера.

## Проверено и признано корректным

| Область | Вывод |
|---|---|
| JWT | HS256, алгоритм зашит в коде — подмена `alg` невозможна; подпись сверяется `compare_digest`; срок проверяется; бан аккаунта убивает действующие токены |
| Массовое присваивание | `PATCH /v1/profile` работает по явному списку полей — `is_blocked`, `needs_review`, `id` не выставить |
| Авторизация в клубах | все изменяющие эндпоинты проверяют `owner_id` и отдают 403 |
| Заказы и платежи | выборки скоупятся по `user_id`; вебхук ЮKassa не верит телу и перезапрашивает статус по API |
| Баллы | клиент не может создать транзакцию `purchase`/`registration` (403); списание идемпотентно по заказу и не уходит в минус |
| SQL | PostGIS-запросы параметризованы, конкатенации пользовательского ввода нет |
| `check --deploy` | замечаний нет: HSTS, SSL-redirect, nosniff, secure-cookies включаются при `DJANGO_DEBUG=0` |
| Секреты | fail-fast не даёт стартовать в проде с дефолтными `SECRET_KEY` / `JWT_SECRET` / паролем БД |
| Rate-limiting | разведён по назначению эндпоинта (D-36); вход — 20/мин |

## Остаётся сделать (не код)

- **Сменить логин и пароль администратора** перед публикацией и ограничить `/admin/` по IP.
- **`X-Content-Type-Options: nosniff` на раздачу `/media/` в nginx** — Django ставит заголовок
  только на свои ответы, а медиа отдаёт nginx. Второй рубеж к находке 3.
- **Уникальность телефона в БД** — миграция с предварительной проверкой дублей. Сейчас
  перехват закрыт на уровне API, но constraint надёжнее.
- **Ротация JWT.** Срок токена 30 дней без механизма отзыва; утёкший токен живёт до конца
  срока. Частично смягчено мгновенным баном. Refresh-токены — отдельная задача.
- **Внешний пентест** перед сколь-нибудь заметным трафиком.
