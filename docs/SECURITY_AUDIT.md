# Базовый аудит безопасности бэкенда (launch-gate §13)

Дата: 2026-08-18. Метод: чтение кода в чувствительных местах (деньги, баллы, личные
данные, загрузка файлов, аутентификация) + `manage.py check --deploy` в прод-конфигурации
+ проверка авторизации на изменяющих эндпоинтах. Каждая находка закрыта тестом.

> Это не пентест и не заключение аудитора. Это внутренняя проверка своими силами,
> покрывающая типовые классы ошибок веб-бэкенда.

---

## Найдено и исправлено

### 1. Сумму заказа определял клиент — критично

**Было:** `POST /v1/orders` брал `total` из тела запроса и на веру. По нему же выставлялся
счёт в ЮKassa и начислялись баллы. Корзину на 50 000 ₽ можно было оформить с `total: 1`,
заплатить рубль и получить товар — прямая потеря денег.

**Стало:** `orders/pricing.py` пересчитывает минимально допустимую сумму по **ценам
каталога** (товар × количество) минус фактически списанные баллы — по реестру транзакций,
а не по заявлению клиента. Заниженная сумма отклоняется с 400. Превышение допускается:
доставку считает клиент, и правил доставки у бэкенда пока нет.

Дополнительно: оплаченный заказ нельзя переоформить с другой суммой (409) — иначе её
меняли бы задним числом.

**Тесты:** 7 — занижение, верная сумма, количество позиций, реально списанные баллы,
заявленные но не списанные баллы, товар вне каталога, доставка сверху.

### 2. Телефон — логин, но менялся без подтверждения

**Было:** `PATCH /v1/profile` принимал `phone`, а вход по SMS ищет аккаунт именно по
номеру, причём поле не уникально. Атакующий присваивал своему аккаунту чужой номер —
дальше вход владельца по SMS мог привести в аккаунт атакующего.

**Стало:** телефон меняется только при первичном заполнении пустого поля, и то с проверкой,
что номер не занят (409). Смена существующего номера игнорируется — для неё нужен отдельный
сценарий с подтверждением по SMS.

**Тесты:** 3 — перехват чужого номера, законное первичное заполнение, занятый номер.

### 3. Тип загружаемого файла определялся по словам клиента

**Было:** проверялись `Content-Type` из заголовка и расширение из имени файла — и то, и
другое присылает клиент. Можно было положить в media `x.html` с любым содержимым: nginx
отдал бы его как страницу, то есть хранимый XSS на домене медиа.

**Стало:** `common/uploads.py` определяет тип по сигнатуре файла (magic bytes), имя и
заголовок игнорируются, расширение подставляет сервер. Разрешены JPEG, PNG, GIF, WebP;
лимит 5 МБ сохранён. Применено во всех четырёх точках загрузки: аватар, фото отзыва,
логотип и обложка клуба.

**Тесты:** 3 — HTML под видом PNG, настоящий PNG с ложным именем и типом, превышение размера.

### 4. Мост «Конструктора» принимал команды от любого origin (проход 2)

**Было:** и админ-консоль (`/admin/merch/`), и `editor.js` на сайте проверяли только поле
`source` **внутри** сообщения `postMessage` — а его задаёт отправитель. Слали обе стороны на
`"*"`. Любой документ, получивший ссылку на окно консоли, мог отправлять ей команды правки
черновика; содержимое правок рассылалось всем.

**Стало:** доверяем `e.origin` (его проставляет браузер). Консоль принимает только с origin
своих фреймов и шлёт адресно; свой origin она передаёт фрейму параметром `console=`, а
`editor.js` принимает команды только от него.

**Почему это не было дырой с выполнением кода:** на сайте правки применяются через
`textContent`, ключи фильтруются, редактор включается только при `?edit=1` внутри iframe,
а сохранение идёт через API с авторизацией.

**Проверено вживую** на dev-стенде: клик внутри фрейма доходит до консоли и открывает правку;
поддельное сообщение с origin самой админки игнорируется.

## Проверено и признано корректным

| Область | Вывод |
|---|---|
| JWT | HS256, алгоритм зашит в коде — подмена `alg` невозможна; подпись сверяется `compare_digest`; срок проверяется; бан аккаунта убивает действующие токены |
| Массовое присваивание | `PATCH /v1/profile` работает по явному списку полей — `is_blocked`, `needs_review`, `id` не выставить |
| Авторизация в клубах | все изменяющие эндпоинты проверяют `owner_id` и отдают 403 |
| Заказы и платежи | выборки скоупятся по `user_id`; вебхук ЮKassa не верит телу и перезапрашивает статус по API |
| Баллы | клиент не может создать транзакцию `purchase`/`registration` (403); списание идемпотентно по заказу и не уходит в минус |
| SQL | PostGIS-запросы параметризованы, конкатенации пользовательского ввода нет |
| `check --deploy` | замечаний нет: HSTS, SSL-redirect, nosniff, secure-cookies включаются при `DJANGO_DEBUG=0` |
| Секреты | fail-fast не даёт стартовать в проде с дефолтными `SECRET_KEY` / `JWT_SECRET` / паролем БД |
| Rate-limiting | разведён по назначению эндпоинта (D-36); вход — 20/мин |

## Остаётся сделать (не код)

- **Сменить логин и пароль администратора** перед публикацией и ограничить `/admin/` по IP.
- **Задать `BACKUP_ENCRYPT_PASSPHRASE`** и хранить пароль ОТДЕЛЬНО от сервера (менеджер
  паролей). Без него дамп со всеми ПДн уезжает в бакет открытым; потеряете — бэкапы станут
  нечитаемы.
- **Отдельный сервисный аккаунт для бакета бэкапов.** По умолчанию скрипт берёт ключ медиа —
  тогда один утёкший ключ открывает и витрину, и все дампы.
- **2FA в админке** (django-otp) — не внедрено: добавляет зависимость и меняет вход. При одном
  администраторе связка «сильный пароль + ограничение по IP + лимит попыток» закрывает основное.
- ~~`X-Content-Type-Options: nosniff` на раздачу `/media/` в nginx~~ — ✅ добавлено в шаблон
  `backend/nginx/mata.conf.example` (вместе с `Content-Disposition: inline`). От владельца
  требуется только скопировать шаблон при деплое, как описано в `docs/DEPLOY.md`.
- **Уникальность телефона в БД** — миграция с предварительной проверкой дублей. Сейчас
  перехват закрыт на уровне API, но constraint надёжнее.
- **Ротация JWT.** Срок токена 30 дней без механизма отзыва; утёкший токен живёт до конца
  срока. Частично смягчено мгновенным баном. Refresh-токены — отдельная задача.
- **Внешний пентест** перед сколь-нибудь заметным трафиком.

# Аудит входа и попытка взлома — 2026-09-04 (D-68)

Метод: чтение кода вокруг аутентификации → правки → 21 регресс-тест атак
(`common/tests_security.py`) → живой пентест по HTTP → проверка инфраструктуры прода.
Задача от владельца: «двухфакторка у всех, вход защитить максимально, потом сломать».

## Найдено и закрыто

### 1. Второй фактор не спрашивали у того, кто его не привязал — критично

**Было:** код требовался только при наличии подтверждённого устройства. Кто не привязал —
входил по одному паролю. На проде так и вышло: у сотрудника 2FA была, **у владельца нет**.
Самая ценная учётная запись (за ней же вкладка выдачи прав) держалась на пароле.

**Стало:** нет устройства → не в админку, а на `/admin/2fa/setup/`. Исключений нет,
владелец в том числе. Запереться нельзя: страница привязки открыта, есть 10 запасных кодов,
крайний случай — `manage.py admin_2fa <логин> --reset` с сервера.

### 2. Открытый редирект на странице кода

**Было:** `?next=` принимал любой адрес. Ссылка `https://api.mata-club.ru/admin/2fa/?next=https://чужой-сайт`
выглядит нашей, а после ввода кода уводит к мошеннику — готовая приманка для фишинга.

**Стало:** `safe_next()` пропускает только внутренние адреса
(`url_has_allowed_host_and_scheme`). Проверено на 7 формах обхода, включая `//`, `\` и `javascript:`.

### 3. Перебор пароля считался только по IP

**Было:** лимит 10 неудач с адреса. Перебор ОДНОЙ учётки со списка прокси не ловился,
а логин владельца предсказуем.

**Стало:** счёт в двух разрезах — по IP (10) и **по логину** (8), с любых адресов.
Удачный вход обнуляет оба.

### 4. Перебор шестизначного кода

**Было:** только пер-девайсная пауза django-otp. С двумя устройствами (приложение +
запасные коды) у подбирающего два независимых бюджета попыток.

**Стало:** общий по человеку лимит (5 попыток → 15 минут) поверх экспоненциальной паузы.
Промах пишется в журнал доступов — владелец видит попытки.

### 5. Мелочи того же слоя

Смена ключа сессии после второго фактора (фиксация сессии), куки `SameSite=Lax` +
`HttpOnly`, `Referrer-Policy: same-origin`.

## Что пробовал сломать — не поддалось

| Атака | Результат |
|---|---|
| JWT `alg=none` (подмена алгоритма, подпись выброшена) | 401 |
| Битая подпись / просроченный / чужой `sub` без переподписи | 401 |
| Обход 2FA прямым адресом, `//`, `..`, методом POST | уводит на привязку |
| Подстановка чужого устройства в свою сессию | не подтверждает |
| Перебор кода / перебор логина | блокировка |
| Эскалация сотрудника через форму пользователя (`is_superuser` в POST) | флаг игнорируется |
| Вкладка «Сотрудники» сотруднику | 403 |
| Приём 1С без токена и с чужим токеном | 401 |
| Утечка трейсбеков (DEBUG) | 404 без стека |

Инфраструктура прода: наружу открыты только 80/443 и SSH; Django напрямую недоступен,
поэтому `X-Real-IP` подделать нельзя (nginx перезаписывает его реальным адресом);
SSH только по ключам, пароли отключены.

## Не дыры, но выглядели ими

- Живой брутфорс формы админки отдаёт **403, а не 429** — CSRF срабатывает раньше лимитера.
  Проверять анти-брутфорс нужно полным флоу (GET формы → POST с токеном), иначе решишь,
  что лимит не работает.

## Остаётся открытым — риск вне кода

Найдено при разборе вопроса владельца «а если кто-то доберётся до команды сброса 2FA».
Сама команда дырой не является: она стоит **за** доступом к серверу, а у того, кто туда
попал, уже есть база и он может сделать себя администратором напрямую. Но проверка цепочки
целиком показала три места, где риск реально выше, чем в админке:

1. **Ключ Yandex Cloud с ролями `admin` + `editor`** лежит на рабочей машине открытым
   текстом (`~/.yc/claude-sa-key.json`) и действует. Даёт секреты Lockbox, удаление и
   пересоздание ВМ, снимок диска и **раздачу прав**. Решение отложено владельцем.
2. **GitHub: правило `protect-main` требует 0 одобрений.** Цепочка «доступ к аккаунту →
   ветка → PR → зелёный CI (проверяет сборку, а не безвредность) → самомерж → автодеплой»
   доводит чужой код до прода примерно за 2 минуты, минуя SSH и админку. Настоящее
   лекарство — двухфакторка на самом GitHub-аккаунте; требование одобрения соло-разработчику
   не подходит (одобрить свой PR платформа не даёт).
3. **SSH-ключ прода без пароля.** Файловые права закрыты (только владелец, SYSTEM,
   администраторы), но процесс, запущенный от имени владельца, ключ прочитает. Пароль
   поставить можно, но тогда нужен включённый `ssh-agent` — иначе ломается автономная
   работа с продом.

Вывод: настоящий периметр системы — **рабочая машина владельца и его аккаунт GitHub**,
а не форма входа в админку. Двухфакторка в панели закрывает кражу пароля и делает это
честно; три пункта выше она не закрывает по определению.
