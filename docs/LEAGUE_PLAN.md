# План работ: «своя лига» в Квартале

Как из стратегии `docs/STRATEGY_KVARTAL.md` сделать работающий продукт. Стратегия отвечает
на вопрос «зачем», этот документ — «что именно делаем, в каком порядке и как поймём, что готово».

Дата: 29.08.2026. Смежные документы: `docs/STRATEGY_KVARTAL.md` (зачем), `docs/WEARABLES_PARTNERS.md`
(часы и заявки), `docs/RESEARCH_MONEYRUN.md` (конкурент), `ECOSYSTEM_API.md` (контракт API).

---

## 1. Что строим

Одна пробежка попадает сразу в несколько зачётов; бегун видит те, которые выбрал сам.
Территории остаются, но становятся одним из режимов, а не единственной игрой.

Шесть зачётов, которые должны заработать:

| Зачёт | Как считается | Кого держит |
|---|---|---|
| Абсолютный | лучшее время / больше километров | быстрых |
| Личный рекорд | улучшил ли ты себя | всех |
| Постоянство | сколько раз за 90 дней | медленных и упорных |
| Своя лига | лучший с поправкой на возраст, пол, уровень | возрастных, женщин, новичков |
| Усилие | вклад по пульсу, а не по темпу | новичков и тех, кто с часами |
| Клубный | сумма попыток команды | социальных и корпоративных |

## 2. Порядок работ и почему такой

Порядок продиктован двумя вещами: **что даёт результат на уже имеющихся данных** и
**что от нас не зависит** (заявки в Garmin и Suunto рассматриваются неделями, Apple требует
аккаунта разработчика).

```
Э1  Лига без троп        ← начинаем сегодня, данные уже есть
Э2  Часы и файлы         ← параллельно: заявки уходят сейчас, код по мере ответов
Э3  Тропы                ← ядро; требует решения по трекам (§4)
Э4  Режимы и онбординг   ← «зачем ты бегаешь» и сборка главного экрана
Э5  Клуб и эстафеты      ← командные зачёты
```

Каждый этап заканчивается тем, что можно показать живому человеку. Ни один не ждёт другого,
кроме Э3 (нужны треки) и части Э2 (нужны ответы партнёров).

## 3. Этап 1 — лига без троп

Смысл: зачёты можно запустить **на тех данных, что уже пишутся** (`runs`: дистанция, время,
дата, захват территорий). Тропы для этого не нужны — нужен период и группа сравнения.

### Что делаем

**3.1. Профиль бегуна.** Для «своей лиги» нужны год рождения, пол и уровень. Сейчас в аккаунте
их нет. Заводим отдельную таблицу (не трогаем `accounts` — её контракт используют все три продукта):

```
runner_profile
  user_id       ссылка на аккаунт, первичный ключ
  birth_year    год рождения (не дата — точная дата нам не нужна, меньше персональных данных)
  gender        м / ж / не указан
  level         новичок / любитель / опытный — сначала со слов бегуна, дальше считаем сами
  weekly_goal   цель на неделю, км (для «прогресса», не обязательна)
  updated_at
```

Все поля необязательные. Не указал — попадаешь в общий зачёт, «своя лига» просто не показывается.
Это важно: спрашивать возраст на входе нельзя, отсекает людей.

**3.2. Группы сравнения.** «Своя лига» = возрастная группа × пол. Возрастные группы берём
стандартные беговые (как на забегах): 18–29, 30–39, 40–49, 50–59, 60+. Отдельно юниоры до 18.
Группа считается на лету из `birth_year`, в базе не хранится — иначе устареет в день рождения.

**3.3. Расчёт зачётов.** Отдельное приложение `league` в бэкенде. Считаем по `runs` за период
(неделя / месяц / 90 дней):

| Зачёт | Формула на текущих данных |
|---|---|
| Абсолютный | сумма километров за период |
| Личный рекорд | лучший результат бегуна за период против его же лучшего за прошлый |
| Постоянство | число пробежек за период (не километры) |
| Своя лига | тот же километраж, но рейтинг строится внутри группы возраст × пол |
| Усилие | пока недоступен — нужен пульс (Э2), в интерфейсе не показываем |
| Клубный | сумма километров участников клуба |

Считаем **на сервере** — как и очки (S-04, античит). Результат кэшируем так же, как рейтинг
сейчас (`leaderboard` уже кэширует).

**3.4. «Ты обошёл N из M».** Главное правило стратегии — никаких проигравших. В каждом зачёте
отдаём не только топ, но и место бегуна плюс сколько человек позади него.

**3.5. API.** Расширяем контракт (`ECOSYSTEM_API.md`):

```
GET  /v1/league/boards?board=<absolute|personal|consistency|mylane|club>&period=<week|month|q90>
     → { board, period, me: {place, of, value, behindNext}, top: [...], group?: {age, gender} }
GET  /v1/runner/profile         → профиль бегуна
POST /v1/runner/profile         → { birthYear?, gender?, level?, weeklyGoal? }
```

**3.6. Экран «Лига» в Квартале.** Вкладка со списком зачётов; по умолчанию открыт тот, что
человек выбрал в онбординге (до Э4 — «своя лига», если профиль заполнен, иначе абсолютный).
Карточка зачёта: моё место, сколько обошёл, топ-10, переключатель периода.
Дизайн — в существующем стиле приложения, без новых визуальных решений (директива владельца).

### Готово, когда

- бегун без профиля видит абсолютный зачёт и постоянство;
- бегун, указавший год и пол, видит «свою лигу» и своё место в ней;
- в каждом зачёте видно «ты обошёл N из M»;
- цифры сходятся с рейтингом, который уже есть (одни и те же пробежки).

### Что нужно от владельца

Ничего. Работаем на имеющихся данных.

## 4. Развилка, которую надо решить до троп

**Сейчас сервер не хранит GPS-треки** — только сводку забега (дистанция, время, флаги).
Так сделано осознанно: приватность, `LAUNCH_READINESS §2`. Трек остаётся на телефоне.

Тропа — это отрезок маршрута, и чтобы засчитать попытку, трек с ним надо **сверить**. Варианты:

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| А. Сверяет телефон | приложение само находит тропы в треке и шлёт результат | треки не покидают телефон | накрутить попытку тривиально: клиенту верить нельзя |
| Б. Сервер хранит треки | как у Strava | всё считается честно | мы начинаем хранить карту передвижений людей |
| **В. Сервер сверяет и забывает** | телефон шлёт упрощённый трек → сервер сверяет с тропами → сохраняет только попытки, трек удаляет через N дней | честный зачёт без постоянного хранения маршрутов | сложнее в реализации; нужен срок хранения и его обоснование |

**Предлагаю вариант В** и оформляю решением в `docs/DECISIONS.md`:
- телефон шлёт трек, прореженный до ~1 точки в 5 секунд, с вырезанными зонами приватности;
- сервер сверяет с тропами района, пишет попытки (тропа, время входа/выхода, длительность);
- сам трек живёт 14 дней (окно для перепроверки и разбора жалоб на накрутку), потом удаляется;
- в настройках — выключатель «участвовать в тропах»: выключен, трек не уходит вовсе.

Решение владельца нужно **до начала Э3**, но не блокирует Э1 и Э2.

## 5. Этап 2 — часы и файлы

Подробности, тексты заявок и что требуется от владельца: `docs/WEARABLES_PARTNERS.md`.
Здесь только место этапа в плане.

| Источник | Когда можем | От кого зависит |
|---|---|---|
| Health Connect (Android) | сразу | ни от кого |
| Файлы GPX / TCX / FIT | сразу | ни от кого |
| Apple Health (iPhone, Apple Watch) | как появится аккаунт Apple Developer | владелец |
| Garmin Connect | после одобрения заявки | Garmin, ~2 рабочих дня на ответ |
| Suunto Cloud API | после одобрения заявки | Suunto, до 2 недель |
| COROS | после одобрения заявки | COROS: очередь раз в месяц, отвечают только выбранным |

Порядок внутри этапа: **Health Connect → файлы → Apple Health → партнёрские API по мере ответов.**
Health Connect первым, потому что через него приходят тренировки с часов COROS, Samsung,
Amazfit, Polar и прочих — без чьего-либо одобрения (`docs/WEARABLES_PARTNERS.md` §1).
Начинаем с импорта файлов: он не зависит ни от кого, сразу закрывает «перенос истории из
ушедших сервисов» (Strava, Nike, adidas отдают архив в GPX/TCX) и даёт готовый механизм,
в который потом воткнутся все остальные источники.

**Общая часть для всех источников** (делаем один раз, дальше только адаптеры):

```
external_workout
  id             наш идентификатор
  user_id
  source         file | apple | garmin | suunto | healthconnect
  source_id      идентификатор тренировки у источника (для идемпотентности)
  started_at, duration_s, distance_m
  avg_hr, max_hr, calories        ← отсюда вырастает зачёт «усилие» и режим «Форма»
  imported_at
  run_id         связь с нашим забегом, если удалось сопоставить
```

Правила, которые надо соблюсти с первого дня:
- **идемпотентность**: повторный импорт той же тренировки не задваивает её (пара `source` + `source_id`);
- **дубли**: тренировка с часов и наш собственный забег в те же минуты — это одно и то же;
  показываем как один забег, очки начисляем один раз;
- **удаление**: удалил у источника — удаляем у себя (у Garmin и Suunto для этого есть уведомления);
- **очки за импорт**: считает сервер по тем же правилам, что и за свой забег, с античитом.

### Готово, когда

Бегун, который бегает с часами и не носит телефон в руке, получает очки и попадает в зачёты.

### Что уже сделано (30.08.2026)

**Health Connect (Android) — работает.** Приложение «Лига» → Профиль → Настройки →
«Часы и приложения». Экран сам показывает, что нужно: поставить Health Connect, дать
доступ, или уже подключено. Синхронизация — при открытии профиля и при возвращении
в приложение, не чаще раза в 15 минут; вручную — кнопкой «Обновить».

Приём на сервере — общий для ВСЕХ источников (`POST /v1/workouts/import`), адаптеры
для файлов, Apple Health и партнёрских API воткнутся в него без переделки. Правила
выше соблюдены с первого дня:

| Правило | Как сделано |
|---|---|
| идемпотентность | уникальность `(user, source, source_id)`; `sourceId` = uuid записи в Health Connect |
| дубли с нашим забегом | пересечение по времени ±20 мин + близкая дистанция (≥ 0.75) → одно событие, очки один раз |
| удаление | «Отключить» отзывает доступ и стирает импорт этого источника на сервере |
| очки | считает сервер, тем же античитом, что и свой забег; суточный лимит общий для своих забегов и импорта — иначе второй источник обходил бы лимит |

Очки начисляем только за беговое (бег, дорожка, ходьба, треккинг). Велосипед и плавание
импортируем и показываем, но в баллы не превращаем.

Осталось в этапе: файлы GPX/TCX/FIT → Apple Health (ждёт аккаунт Apple Developer) →
партнёрские API по мере ответов.

## 6. Этап 3 — тропы

Ядро лиги. Начинается после решения по §4.

**6.1. Модель.**

```
trail                     тропа
  id, name, city
  geometry                линия маршрута (PostGIS — он у нас уже стоит)
  length_m, elevation_m
  created_by              null = найдена автоматически
  is_public

trail_attempt             попытка
  id, trail_id, user_id, run_id
  started_at, duration_s
  avg_hr                  если пришло с часов
  is_valid, invalid_reason
```

**6.2. Сверка попытки.** Трек считается прохождением тропы, если: заходит в стартовую зону,
выходит из финишной, идёт в ту же сторону, не отклоняется от линии больше допуска, и время
между входом и выходом правдоподобно. Время попытки — по точкам входа и выхода, не по всему забегу.

**6.3. Рождение троп.** Сначала **вручную**: клуб или бегун рисует тропу по своему маршруту.
Автоматический поиск (кластеризация похожих треков) — потом: он бесполезен, пока нет плотности
пробежек в одном месте, а на старте её не будет.

**6.4. Четыре доски на тропе:** быстрейшие · мой прогресс · чаще всех за 90 дней · моя лига.
Плюс клубный зачёт.

**6.5. Поправки в «своей лиге»:** набор высоты, мороз, ветер. Абсолютная доска остаётся сырой —
это принципиально: у быстрых должен быть честный «сырой» рейтинг.

**6.6. Приватность:** зона вокруг дома. Тропа не может начинаться внутри неё; попытки в зоне
не засчитываются и не показываются.

**6.7. Античит:** невозможные скорости, ускорения, велосипед и машина. Часть проверок у нас
уже есть для забегов — переиспользуем.

### Готово, когда

Человек, который бегает один и тот же парк, открывает приложение ради тропы.

## 7. Этап 4 — режимы и онбординг

- вопрос при первом запуске «зачем ты бегаешь»: здоровье · соревноваться · с людьми ·
  разгрузить голову;
- главный экран собирается под ответ; остальное — в «ещё режимы»;
- **мирный режим территорий**: захваченное нельзя отобрать (для тех, кого отпугивает PvP);
- переключение режимов в настройках в любой момент.

### Готово, когда

Доля бегунов, у которых включён не-территориальный режим, больше половины.

## 10. Метрики этапов

| Этап | Что смотрим | Ориентир |
|---|---|---|
| Э1 | доля бегунов, открывших «Лигу» второй раз | > 40% |
| Э1 | доля заполнивших год и пол | > 30% |
| Э2 | доля тренировок, пришедших с часов и файлов | > 25% |
| Э3 | повторные попытки на тропе | ≥ 3 на тропу в месяц |
| Э4 | доля с не-территориальным режимом | > 50% |
| Общее | удержание на 8-й неделе | > 35% |

## 11. Риски

| Риск | Лечение |
|---|---|
| Пустые доски на старте (мало людей) | «мой прогресс» и «постоянство» работают в одиночку; зачёты по городу, а не по стране |
| Возраст и пол — персональные данные | необязательны, храним год (не дату), согласие при заполнении |
| Пульс — данные о здоровье | отдельное согласие, не передаём третьим лицам, не используем в рекламе (требование Apple) |
| Заявки к Garmin и Suunto затянутся | начинаем с файлов и Health Connect, они ни от кого не зависят |
| Накрутка на тропах | серверная сверка, античит, хранение трека 14 дней для разбора |
| Распыление на восемь режимов | этапы; в каждом один режим доводится до конца |

## 12. Что требуется от владельца

| Когда | Что | Зачем |
